## 3. 특기 사항

### 가. 연번 1·2는 동일 증상의 원인임

브리지 프로세스 및 Theia 프로세스 모두 정상 가동 중이며, `~/.iris-light/runtime/iris_ide_state.json`에 `bridge_port`와 토큰이 정상 기재되어 있음을 확인하였음. 그럼에도 `getActiveEditor` 조회 결과가 `{ "editor": null }`로 반환됨.

반환값이 `null`인 사실 자체가 원인을 특정함. 프런트엔드가 단 1회라도 상태를 전송하였다면 `pushBridge`가 `JSON.stringify(null || {})` = `"{}"`를 전송하므로 값은 `{}`가 되어야 함. 따라서 **전송이 전혀 이루어지지 않았음이 확정됨.** 유일한 이탈 경로는 `if (!this.bridgePort) return;`이며, 가동 중인 프런트엔드의 `bridgePort`가 0으로 판단됨.

#### 조치 시 실측 보정 (2026-09-17)

위 추론 중 이탈 경로 특정은 **부분적으로만 타당하였음.** 쿼리스트링 소실로 `bridgePort`가 0이 되는 경로는 실재하였으나, 포트·토큰이 정확한 상태에서도 전송이 불가함을 실측으로 확인하였음.

Theia 페이지와 브리지는 포트가 상이하여 cross-origin이며, 브리지가 `Access-Control-Allow-Origin`을 반환하지 아니하므로 preflight가 필요한 요청은 물론 **단순 POST까지 `Failed to fetch`로 차단되었음.** 즉 `setEditorState`·`pollPendingCommands`가 단 1회도 성공할 수 없는 상태였음. 따라서 `if (!this.bridgePort) return;` 외에 **`fetch(...).catch(() => undefined)`가 실패를 삼키는 경로가 추가 이탈 경로로 존재함.**

`control_surface.py:229-236`이 동일 사유로 이미 ACAO를 부가하고 있어, 같은 방식을 브리지 2종(`standalone-bridge.js`·`iris-ide-bridge-server.ts`)에 적용함.

### 나. 연번 1의 파생 영향 (별도 연번 미부여)

`IrisIdeBridgePoller`도 동일 경로로 포트를 취득하므로(`iris-ide-bridge-poller.ts:34-39`) 동시에 정지함. 폴러 정지 시 `standalone-bridge.js`의 `openFile`이 `enqueueFrontend` 타임아웃 후 `catch` 블록에서 `editorState`만 갱신하고 `{ opened: true, via: 'bridge_fallback' }`을 반환함(`standalone-bridge.js:143-146`). 즉 **파일이 실제로 열리지 않았음에도 성공으로 보고됨.** 진단 시 응답의 `via` 필드를 폴러 생존 판정 지표로 활용할 수 있음.

단 `via` 지표에는 두 가지 유의 사항이 있음. 첫째, 기동 직후 최초 개방은 Monaco 초기화로 `enqueueFrontend`의 3.5초를 초과할 수 있으므로 1회 워밍업 후 판정하여야 함. 둘째, UI 스레드 차단 시에도 동일하게 폴백하므로 **연번 17과 구별되지 아니함.** 폴백이 아닌 확증 지표로는 프런트엔드만 생성하는 `languageId` 필드의 존재 여부를 사용함.

### 다. 연번 11 — 완료 (2026-09-17). 「정면 상충」은 조건부였음

최초 총괄표는 연번 10·11을 「정면 상충」으로 기술하였으나, 실측 결과 IDE 개방·라이브 타이핑 트리거는 렌더된 HTML이 아니라 **스트리밍 원문**(`state["raw"] += chunk`)을 소비함. 따라서 연번 10을 렌더 계층에서만 구현하면 트리거는 영향받지 않음.

실제 모순은 다른 지점에 있었음. 시스템 프롬프트는 `project.write_file`을 정상 경로로 요구하는데, 트리거는 채팅 펜스에만 묶여 있어 **도구로 쓰면 연출이 없고, 채팅에 코드를 뱉으면 연출이 뜨는** 정반대 상태였음.

조치: `project.write_file` 성공을 1급 IDE 개방 트리거로 확정(`_note_tool_file_write` + `_first_class_ide_trigger` 래퍼), 펜스 감지는 폴백으로 격하. 자검 `iris.ui._check_chat_render_ide_trigger` 통과. 선결이 풀린 뒤 archify B단계(`diagram.render` · `integrations/archify/` · `diagram_preview.py`)까지 도입·자검 통과.

### 라. 기획 대비 실제 동작은 정상임

`main_window.py`의 시스템 프롬프트가 Hermes 내장 터미널 사용을 금지하고, 파일 작성은 `project.write_file`, 실행은 `project.run`을 통해 바인딩된 IDE 통합 터미널에서 수행하도록 명시하고 있음. 즉 **실행 위치는 기획대로 IDE 내부이며**, Hermes는 지시 주체에 해당함. 조치 소요는 실행 위치가 아니라 채팅 표시 계층에 한정되며, 그중 연번 11은 완료·**연번 10만 잔여**임.

### 마. 기존 자체점검 스크립트의 한계

`iris/system/_check_iris_ide_bridge.py`는 Theia 프런트엔드 없이 브리지 단독으로 구동하므로, `openFile`이 위 「나」항의 `bridge_fallback` 경로로 통과함. 따라서 **연번 1을 검출하지 못하는 false-green임.** 연번 1의 회귀 시험은 실제 프런트엔드가 결합된 상태에서 수행하여야 함. 아울러 동 스크립트는 `run_terminal_command` 단계에서 폴백이 없어 HTTP 400으로 실패하므로(조치 전부터 동일), 완료 게이트로 사용할 수 없음.

이에 따라 자체점검 2건을 신설함.

| 스크립트 | 대상 | 방식 | 소요 |
|---|---|---|---|
| `iris/system/_check_iris_ide_bridge_state.py` | 1·2·3 | 헤드리스 — 신원 승계 로직(node), 브리지 단독 정규화, 컨텍스트 예산 상한 | 약 5초 |
| `iris/system/_check_iris_ide_bridge_nav.py` | 1 (+3·17) | 실제 Theia·브리지·`QWebEngineView` 기동 후 **쿼리스트링 소실 재현** | 약 25초 |

`_check_iris_ide_bridge_nav.py`는 IRIS IDE 실행 중에 구동하지 말 것 (런타임 상태파일 공유).

### 바. 연번 9는 조치하지 아니함 (설계 결정, 2026-09-17)

본 제품의 설계는 **클라우드·로컬 모델 + Hermes 조합**이며, Hermes는 선택이 아니라 필수 구성요소임(설치 프로토콜 포함). 도구 호출 루프를 IRIS 내부에 별도 구현하면 Hermes가 이미 수행하는 기능을 이중으로 유지하게 되므로 **배관을 잇지 아니하고, Hermes를 끄는 입구를 제거하는 방향으로 종결함.**

근거는 코드가 이미 동 계약을 전제하고 있다는 점임. `settings.py:18`의 기본값이 `True`이고, 메일·캘린더는 Hermes 미사용 시 이미 명시적 실패로 처리하고 있었음(`main_window.py:3952-3955·4201-4204`). 아울러 커스텀 API 모델도 Hermes가 `provider="custom"`으로 수용하므로(`hermes_client.py:82-89`) 「클라우드 모델 + Hermes」 조합은 성립함. 즉 연번 9는 사용자가 Hermes를 **명시적으로 끈** 상태에서만 발현되는 사항이었음.

조치 범위는 다음 3개소이며, 끄는 경로를 없앰으로써 연번 9의 전제 자체를 소멸시킴.

| 대상 | 조치 |
|---|---|
| `settings_dialog.py` | 「Hermes Agent 사용」 체크박스 및 `LightSettingsSelection.hermes_enabled` 제거 |
| `main_window.py:6242` | `self._settings.hermes_enabled = sel.hermes_enabled` 제거 |
| `control_bindings.py` | `settings.set`의 `hermes_enabled` 대입을 **명시적 거절**로 대체 (조용한 무시 금지) |

컨트롤 액션 경로는 특히 유의 사항이 있었음. `settings.set`으로 `hermes_enabled=false`가 수용되면 **모델이 자기 도구를 스스로 끌 수 있으며**, 이후 도구가 필요한 요청에 「완료하였음」으로 오보고할 수 있음. 따라서 무시가 아니라 오류 반환으로 처리함.

**잔여 경로 1건**: 환경변수 `IRIS_HERMES_ENABLED`(`settings.py:66`)로는 여전히 끌 수 있음. 개발·시험용 우회로로 존치하였음. 이를 제거하면 `if not hermes_enabled` 가드 8개소가 사문화되므로 별건으로 판단함.

회귀 방지: `iris/ui/_check_hermes_required.py` 신설 (기본값 `True` · 설정 화면에 스위치 부재 · `settings.set`이 끄기를 거절). 약 2초, 오프스크린.

### 사. 연번 19·20 실측 결과 (2026-09-17)

#### 연번 19 — 근본 원인 미확정임

정지·플래그 조합별 실측을 수행하였으나 **검은 화면을 재현하지 못하였음.** UI 스레드를 8초간 통째로 정지시켜도 데스크톱 표시는 정상을 유지하였음. 초기 관측에서 검게 나온 1건은 직전 시험의 잔류 창에 의한 가림으로 판명되어 **오탐**이었음.

다만 플래그 조합 간 차이는 실재함. 조치 전 `--disable-gpu --disable-gpu-compositing`은 **매 기동마다** `ContextResult::kFatalFailure` 3건과 컨텍스트 생성 실패 6건을 발생시킨 반면, `--disable-gpu-compositing` 단독은 0건이었음. 첫 표시 시간은 0.92초 대 0.99초로 차이가 없었음(각 2회).

즉 `--disable-gpu`는 GPU 프로세스 기동을 막지 못한 채 공유 컨텍스트 생성만 실패시키고 있었으므로, 해당 플래그의 존재 이유(주석의 「첫 표시 시 수분간 정지」)가 성립하지 아니하였음. 이에 기본값에서 제거하였음.

아울러 조치 전에는 `QTWEBENGINE_CHROMIUM_FLAGS`에 무엇을 넣어도 `--disable-gpu`가 덧붙어 A/B가 불가하였음. 사용자 지정이 있으면 그대로 두도록 변경하여 **재빌드 없이 A/B가 가능**함.

| 시험 | 플래그 | 결과 |
|---|---|---|
| 조치 전 | `--disable-gpu --disable-gpu-compositing` | 표시 정상 · GPU 치명 오류 3건 · 첫 표시 0.99초 |
| 조치 후 | `--disable-gpu-compositing` | 표시 정상 · GPU 치명 오류 0건 · 첫 표시 0.92초 |
| 참고 | `--use-gl=desktop` 부가 | **프로세스 즉사** (0xC0000409) — 사용 금지 |

#### 연번 20 — 탭 드래그는 구조적으로 불가함

Theia 편집기 탭은 Lumino `TabBar`가 처리하며, `_evtPointerDown`이 `event.preventDefault()`를 호출함(`@lumino/widgets/src/tabbar.ts:895`). Chromium은 `mousedown`에서 기본 동작이 취소되면 네이티브 드래그를 시작하지 아니하므로 **`dragstart`가 발생할 수 없음.** 따라서 `uriFromDragEvent`의 `.lm-TabBar` 계열 폴백 2개는 도달 불가 코드였고, 「탭도 지원됨」이라는 잘못된 인상만 주고 있었음.

반면 익스플로러는 HTML5 드래그를 사용함(`file-tree-widget.js:94·99` — `draggable` + `onDragStart`)이고, 노드 `div`에 `id = node.id = file:///…`가 부여되므로(`tree-widget.js:507`) 기존 경로가 그대로 성립함. **즉 드래그 출처는 익스플로러뿐임.**

조치는 도달 불가 분기를 제거하고 탭에는 컨텍스트 메뉴 「Attach to IRIS Chat」(`SHELL_TABBAR_CONTEXT_MENU`)을 신설하는 방식으로 함. 탭 우클릭 시 Theia가 선택 항목에 `{ uri }`를 올려두므로(`tab-bars.js:116`) 이를 읽어 `chat.attach`로 전달함.

### 아. 연번 21 — 기본 창 OS 파일 드롭 (2026-09-18, 미해결)

#### 증상 분리 (실측)

| 경로 | 결과 |
|---|---|

즉 첨부·칩 파이프(`attach_drop_paths`)는 살아 있고, **OS OLE가 기본 창에 이벤트를 주지 않는 계층**이 병목임.

#### 원인 가설 (확정에 가까운 것)

1. **Qt `DragEnter` 미도달** — `acceptDrops`·자식 arm·`eventFilter`가 있어도 `dnd.log`에 Enter가 한 줄도 없음. 코드 게이트(`mime_has_attachable`) 이전에 실패.
2. **Frameless + 투명/합성** — `FramelessWindowHint` + 과거 `WA_TranslucentBackground`/전역 transparent QSS 조합에서 Win32 히트테스트·OLE 타겟 등록이 깨질 수 있음. 프로브 시 `WS_EX_ACCEPTFILES`는 Qt만으로는 꺼져 있었음(OLE 전용 경로).
3. **외부 요인 후보** — UIPI(관리자 Iris ↔ 일반 Explorer), 드롭 좌표가 Iris HWND가 아닌 뒤쪽 창. 다만 `+`·IDE companion이 되는 PC에서도 재현되어 **앱 HWND/OLE 쪽이 주원인**으로 봄.

#### 시도한 개선 (남긴 것 / 되돌린 것)

| 시도 | 결과 |
