## 1. 결론

구현은 아이리스 채팅 실행만 세 단계다. 헤르메스는 유지한다.

1단계의 본 경로는 코드에 있다. 같은 모델로 채팅 둘의 루프가 동시에 가고, 화면을 바꿔도 뒤 루프는 취소되지 않는다. 비동기 이어짐이 슬롯을 놓고, 모델은 아직 게이트웨이 기본값이다. 그 두 곳이 2단계다.

3단계 Git worktree는 열지 않았다.

---

## 2. 구조

```text
보이는 채팅에서 전송
  └─ submit(대화 id)
       └─ 슬롯이 비었고 동시 수 < 2
            └─ _execute_user_turn 이 슬롯을 묶음
                 ├─ 동기면 그 대화 DB와 그 슬롯의 워커
                 └─ 첨부·자료·이전 대화 검색이면 콜백에서 바인딩이 풀림
                      └─ 화면 대화의 기록과 창 전역 프롬프트
                           └─ set_inference_model → chat/completions
전환
  └─ 화면·구체·TTS만 교체. 워커는 유지
쓰기
  └─ SessionWriteLock. 못 집으면 그 HTTP 요청만 대기
```

갈라지는 지점은 슬롯 바인딩의 `finally`와, 채팅 워커의 전역 모델 쓰기다. 위키 경로는 보관이고 실행 키가 아니다.

## 3. 코드 리뷰

| 지점 | 지금 한 일 | 다음 단계로 남긴 이유 |
|---|---|---|
| `ChatSession` | 대화별 DB 기록 | 실행 슬롯은 `ChatRunSlot`이 맡음 |
| `ChatRunMap` / `SlotAttr` | 워커·점유·이어하기·부분 응답을 대화 id에 둠 | 바인딩이 동기 구간에만 있음 |
| `UserTurnDispatcher` | 동시 2, 같은 대화는 한 줄 | 음성 정지가 대기열 전체를 지움 |
| `_load_conversation` | 전환이 워커를 취소하지 않음 | 삭제된 대화의 워커는 계속 돔 |
| 토큰 `*_for_turn` | 화면이 아니면 DB와 `pending_partial` | 사용자 말풍선은 화면 로그에 붙음 |
| `SessionWriteLock` | 프로젝트 하나, 위키 경로마다 하나 | 이동·PDF·폴더 열기는 표 밖. 경로는 문자열 그대로 |
| `set_inference_model` | 매 채팅 런이 기본 모델을 씀 | 2단계에서 채팅 런은 이 호출을 멈춤 |
| `stream_chat` | `model` 필드만 있음 | `provider`와 세션 헤더가 없음 |
| 음성·구체 | 화면 채팅만 따름. `CAP` 8은 슬롯에 있음 | 모델 피커는 여전히 창에 하나 |

하지 않은 일. 헤르메스 소스, 게이트웨이 프로세스 분리, `iris/core`, Git worktree, 설치본 `/v1/capabilities` 실측, 이번 최신화에서의 검사 재실행.

## 4. 구현 단계

### 1단계. 세션 실행

명세는 `다중채팅-동시작업-1단계-구현보고서.md`. 달성 여부는 `다중채팅-동시작업-1단계-분석보고서.md`.

들어간 것. 대화 id별 슬롯, 전환 시 취소 제거, 동시 2, 화면 전용 구체·TTS, 프로젝트·위키 쓰기 잠금, 이어하기 8을 슬롯에 유지.

남은 것. 비동기 콜백의 슬롯 바인딩, 창 전역 프롬프트 조각, 잠금 표 밖의 쓰기, 채팅 삭제와 음성 정지의 범위.

### 2단계. 요청 단위 모델

명세는 `다중채팅-동시작업-2단계-구현보고서.md`.

채팅 워커는 `set_inference_model`을 멈추고, 그 요청에 `model`과 `provider`를 싣는다. 슬롯이 모델을 기억한다. 비동기 이어짐은 그 슬롯에 다시 묶인다. 세션 헤더는 같은 완료 API에 대화 id만 붙인다. 헤르메스 소스·게이트웨이 프로세스·`iris/core`는 그대로 둔다.

완료 기준. 같은 게이트웨이에서 두 런이 동시에 있고, 각 요청의 모델이 유지된다. 화면을 바꿔도 뒤 채팅의 기록과 프롬프트가 앞 채팅으로 옮겨 가지 않는다.

### 3단계. 코딩 병렬

같은 저장소를 고치는 채팅은 `git worktree add`로 폴더를 나눈다. 그 세션의 IDE·터미널만 그 폴더를 본다. 끝나면 사용자가 본 트리로 가져온다. 자동 병합은 넣지 않는다. 위키 노트로 이 사본을 만들지 않는다.

완료 기준. 본 트리에 들어가는 변경은 사용자가 확인한 뒤뿐이다.

---

## 5. 개선안

1. 실행 맵은 있다. 빈 자리는 그 맵이 비동기 구간과 프롬프트 조립까지 닿지 않는 것이다.
2. 전환 취소는 빠졌다. 빈 자리는 콜백이 화면 위젯과 화면 대화 id를 쓰는 것이다.
3. 쓰기 잠금은 있다. 빈 자리는 표 밖의 쓰기와 정규화되지 않은 경로다.
4. 모델 필드는 아직 빈 자리다. 2단계가 채운다.
5. worktree는 빈 자리가 아니다.

## 6. 차용

| 이름 | 가져올 부분 | 이번에 가져오지 않는 이유 |
|---|---|---|
| OpenAI conversation | 대화 id로 기록과 다음 호출을 잇는 단위 | id는 이미 있음. API 제품으로 교체하지 않음 |
| Cursor 서브에이전트 | 뒤 루프가 화면을 막지 않음 | 1단계에 반영됨. 화면·런타임은 가져오지 않음 |
| ReAct 궤적 | 도구 기록은 그 세션 안에만 | 논문 구현체를 넣지 않음 |
| 헤르메스 요청 단위 모델 | 2단계. `model` + `provider`. 완료·runs·세션 채팅에 실을 수 있음 | 소스 수정과 `session_model_pool`은 전제가 아님 |
| 헤르메스 세션 헤더 | `X-Hermes-Session-Id`를 지금 POST에 | Sessions API로 경로를 바꾸지 않음 |
| Git worktree | 3단계 | 2단계 조건이 아님 |
| vLLM | 로컬 배치용으로 문서에만 있음 | 평소 경로가 원격 API라 1·2단계 조건이 아님 |

헤르메스 판단.

| 용도 | 맡는 일 | 판단 |
|---|---|---|
| 일상 | 대화, 메일·일정, 위키, 조사 | 유지. 채팅 런의 전역 모델 쓰기만 멈춤 |
| 개발 | IDE, 파일, 터미널 | 유지. 경계는 잠금과 3단계 사본 |
| 프로젝트 | 저장소 수정, 긴 작업 | 유지. 이어하기 8은 자동 턴 브레이크 |

## 7. 조치

1. 2단계는 `다중채팅-동시작업-2단계-구현보고서.md`만 구현한다.
2. 1단계 잔여(잠금 표, 삭제 시 취소, 음성 대기열)는 그 명세에 넣지 않는다.
3. 3단계는 같은 저장소를 동시에 고쳐야 할 때 연다. 자동 병합은 제외한다.
4. 착수 전 설치본의 `/v1/capabilities`와 `max_concurrent_runs`를 본다.
