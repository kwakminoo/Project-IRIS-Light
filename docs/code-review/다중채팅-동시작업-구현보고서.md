# 다중 채팅 동시 작업 구현 보고서

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-IMPL-2026-1008-01 |
| 작성일 | 2026-10-08 |
| 관련 | IRIS-REV-2026-0930-02. 2026-10-02자 IRIS-IMPL-2026-1002-01을 이 문서로 갈아 씀 |
| 대상 | Iris Light 메인 채팅 실행 |
| 목적 | 같은 원격 모델로 채팅마다 작업을 동시에 두기 위한 구현 단계 |

확인일 2026-10-08. `ChatSession`은 대화 id와 DB 기록만 나눈다. `ChatTurnGate.busy`, `UserTurnDispatcher._active`, `MainWindow._chat_worker`는 각 하나다. `_on_user_text`는 `session_id` 없이 전송한다. `_load_conversation`은 `busy`이면 `conversation_switch`로 취소한다.

---

## 1. 결론

구현은 아이리스 채팅 실행만 세 단계로 나눈다. 헤르메스는 유지한다. 평소 경로는 원격 API의 한 모델이다. 그 모델은 요청을 여러 건 받는다. 막힌 곳은 아이리스의 실행 슬롯 하나다.

1단계는 세션 분리다. 키는 위키가 아니라 대화 id다. 모델 호출 방식과 Git worktree는 열지 않는다. 이어하기 상한 8은 자동 다음 턴의 브레이크이며 이 단계의 동시 개수와 별개다.

---

## 2. 구조

```text
키보드 _on_user_text
  └─ UserTurnDispatcher.submit          ← 활성 턴 하나. 키보드에 대화 id 없음
       └─ _execute_user_turn
            ├─ 이어하기·도구 카운트 리셋  ← 창 전역
            ├─ ChatTurnGate.begin / busy  ← 하나
            └─ _chat_worker 하나 → Hermes
                 ├─ 토큰 → 지금 화면과 지금 ChatSession
                 ├─ 도구 → control_surface (쓰기 잠금 없음)
                 └─ 종료 → decide_followthrough (CAP 8)
전환 _load_conversation
  └─ busy 이면 _cancel_current_turn(conversation_switch)  ← 여기서 진행 중 작업이 죽음
위키 projects/<슬러그>/chats/<대화 id>.md  ← 보관. 실행 슬롯 아님
```

갈라지는 지점은 전환의 취소와, 워커·점유가 대화 id에 없고 창에 하나인 지점이다.

---

## 3. 코드 리뷰

| 지점 | 이번 구조에서 한 일 | 동시 작업을 막은 이유 |
|---|---|---|
| `ChatSession` | 대화별 기록 | 실행은 안 나눔 |
| `UserTurnDispatcher` | 턴을 한 줄로 대기 | `_active`가 하나 |
| `_on_user_text` | 키보드 전송 | 대화 id를 안 실음 |
| `ChatTurnGate` | 진행 턴 하나 | `busy`가 창 전체 |
| `_chat_worker` | Hermes 한 런 | 다음 채팅이 이 칸을 비움 |
| `_load_conversation` | 화면의 기록 교체 | 생성 중이면 취소 |
| `_followthrough_count` | 자동 다음 턴, 상한 8 | 창에 하나. 전환 시 0 |
| `set_inference_model` | 런타임 기본 모델 | 1단계 범위 밖. 같은 모델이면 호출을 유지 |
| 위키 경로 | 채팅 글 보관 | 프로젝트 안에 채팅이 여러 개 |
| 음성·구체 | 창의 마이크와 `AppState` 하나 | 어느 채팅 것인지 규칙이 없음 |

하지 않은 일. 헤르메스 소스, 게이트웨이 프로세스, `iris/core`, Git worktree, 설치본 `/v1/capabilities` 실측.

---

## 4. 구현 단계

### 1단계. 세션 실행

대화 id마다 워커, 점유, 이어하기, 부분 응답을 둔다. 전환은 화면만 바꾼다. 동시 루프는 2다. 모델은 지금 모델 하나다. IDE·`project.write_file`·터미널은 잠금 하나다. 위키는 노트 경로만 잠근다. 구체와 음성은 화면에 있는 채팅만 따른다. 명세는 `다중채팅-동시작업-1단계-구현보고서.md`.

결과. 조사와 서로 다른 문서 작업은 채팅마다 동시에 간다. 코딩 쓰기는 한 채팅만 한다.

완료 기준. 채팅을 옮겨도 진행 중 답이 취소되지 않는다. 두 채팅이 같은 파일을 동시에 고치지 않는다.

### 2단계. 요청 단위 모델

채팅마다 다른 모델을 쓸 때 연다. `set_inference_model`(`scope: main`)을 멈추고, 그 요청에 `model`과 `provider`를 싣는다. 헤르메스 소스·게이트웨이 프로세스·`iris/core`는 그대로 둔다. 공개 문서 `api-server.md`(커밋 `a28a5d03`, 2026-10-08 확인)에 요청 단위 모델이 있다.

결과. 모델이 다른 두 채팅이 기본 모델을 덮어쓰지 않는다.

완료 기준. 같은 게이트웨이에서 두 런이 동시에 있고, 각 요청의 모델이 유지된다. 착수 전 설치본의 `/v1/capabilities`와 `max_concurrent_runs`(문서 기본 10, 초과 시 429)를 본다.

### 3단계. 코딩 병렬

같은 저장소를 고치는 채팅은 `git worktree add`로 폴더를 나눈다. 그 세션의 IDE·터미널만 그 폴더를 본다. 끝나면 사용자가 본 트리로 가져온다. 자동 병합은 넣지 않는다. 위키 노트로 이 사본을 만들지 않는다.

결과. 두 코딩 채팅이 본 작업 트리를 동시에 고치지 않는다.

완료 기준. 본 트리에 들어가는 변경은 사용자가 확인한 뒤뿐이다.

---

## 5. 개선안

빈 자리는 네 곳이다.

1. 대화 id를 키로 한 실행 맵. 워커, 점유, 이어하기, 부분 응답.
2. 전환에서 `conversation_switch` 취소 제거. 토큰은 그 대화 기록에만 첨부.
3. 쓰기 잠금. 읽기와 조사는 잠금 밖.
4. 구체·음성·정지 버튼을 포그라운드 세션에 연결.

모델 필드와 worktree는 이 빈 자리가 아니다.

## 6. 차용

| 이름 | 가져올 부분 | 이번에 가져오지 않는 이유 |
|---|---|---|
| OpenAI conversation | 대화 id로 기록과 다음 호출을 잇는 단위 | API 제품으로 교체하지 않음. id는 이미 있음 |
| Cursor 서브에이전트 | 뒤 루프가 보고 있는 화면을 막지 않음 | 화면·런타임을 가져오지 않음 |
| ReAct 궤적 | 도구 기록은 그 세션 안에만 둠 | 논문 구현체를 넣지 않음 |
| 헤르메스 Sessions·Runs API | 2단계에서 요청 단위 모델·런 정지 | 1단계는 같은 모델이라 지금 호출을 유지 |
| Git worktree | 3단계에서 폴더를 나눔 | 1단계의 조사·서류에는 폴더 사본이 필요 없음 |
| vLLM | 찾지 못함이 아님. 로컬 배치용 | 평소 경로가 원격 API라 1·2단계의 조건이 아님 |

## 7. 헤르메스 판단

| 용도 | 맡는 일 | 판단 |
|---|---|---|
| 일상 | 대화, 메일·일정, 위키, 조사 | 유지. 세션만 나누면 같은 모델로 병렬 |
| 개발 | IDE, 파일, 터미널 | 유지. 경계는 아이리스 잠금과 3단계 사본 |
| 프로젝트 | 저장소 수정, 긴 작업 | 유지. 이어하기 8은 자동 턴 브레이크 |

근거. 전환 시 취소와 전역 모델 쓰기는 아이리스가 슬롯을 하나 둔 결과다. 교체해도 그 문제는 새 런타임 위에 남는다.

## 8. 조치

1. 1단계만 구현한다. 명세는 `다중채팅-동시작업-1단계-구현보고서.md`.
2. 2단계는 채팅마다 모델을 다르게 쓸 때, 설치본 능력 확인 뒤에 연다.
3. 3단계는 같은 저장소를 동시에 고쳐야 할 때 연다. 자동 병합은 제외한다.
