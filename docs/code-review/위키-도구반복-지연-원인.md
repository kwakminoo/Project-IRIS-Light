# 위키 요청이 길고 도구가 반복되는 이유

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-CR-20261006-WIKI |
| 작성일 | 2026-10-06 |
| 관련 | `obsidian-vault/Iris Light/Wiki LLM 설계.md` (2026-07-30), 스킬 `iris-wiki`, `iris/ui/control_actions/wiki.py` |
| 대상 | 채팅에서 위키를 저장·조회·옮길 때의 도구 루프 |
| 목적 | 기획과 맞는 곳, 어긋난 곳, 실패·보안·고칠 빈자리를 고정한다 |

## 1. 결론

짧은 위키 요청도 Hermes 도구 연쇄로 간다. 로컬 한 방 실행은 꺼져 있다.

한 번의 저장이 목록 → 검색 → 분류 모델 → 쓰기 → 열기로 늘어나고, 답이 “끝”처럼 보여도 감독이 최대 8번 다시 같은 목표를 돌린다. 페이지를 여러 장 받으면 장마다 추출과 분류가 붙는다. 스킬은 “한 번에 가져와라”고 적혀 있으나, 코드는 그 반복을 막지 않는다.

기획(검색해서 넣고, 사용자 폴더에만 쓰고, 애매하면 inbox)의 뼈대는 있다. 2026-07-30 설계 문서의 “미구현” 표기는 현재 코드보다 뒤처져 있다.

## 2. 확인한 사실

코드 기준. 이번 조사에서 DB 건수는 세지 않았다.

| 사실 | 위치 |
|---|---|
| 채팅 위키는 항상 Hermes로 넘긴다 | `wiki_requests_go_to_hermes()` 가 항상 참. `main_window` 는 그 참일 때 `try_wiki_command` 와 로컬 저장을 타지 않는다 |
| 로컬 명령 파서는 남아 있다 | `parse_wiki_command` → `execute_wiki_command`. 채팅 입구에서는 호출되지 않는다 |
| 저장·검색마다 분류기를 연다 | `filing_kwargs` → Ollama 프로브 4초, 임베딩, 필요 시 분류 JSON 최대 45초 |
| 검색은 지식 트리를 먼저 맞춘다 | `wiki.search` 와 채팅 주입 모두 `sync_knowledge_notes` |
| 이어 하기 상한은 8이다 | `turn_followthrough.CAP`. 이 저장소 안에 Hermes 도구 횟수 상한은 없다 |
| 도구 성공 없이 “저장했습니다”면 다시 돌린다 | `decide_followthrough`. 목표에 「저장」이 있고 마지막 문장이 계속·이어서·저장하겠이면, 도구가 성공해도 다시 돌린다 |
| 답 문장을 앱이 고치지는 않는다 | `settle_wiki_claim` 은 받은 글을 그대로 반환한다 |
| 여러 페이지 상한은 80, 목록 한 페이지는 40 | `wiki.import_pages`, `wiki.list_notes` |
| 문단 번역은 24회에서 멈춘다 | `wiki_ops._MAX_TRANSLATE_CALLS`. 나머지는 원문만 두고 성공으로 끝난다 |
| 사용자 경로의 `..` 와 `docs/` 쓰기는 거부한다 | `IrisWiki._normalize_user_rel` |

## 3. 구조

요청이 화면 답까지 가는 길. **이번 지연은 `로컬 명령` 이 아니라 `Hermes 도구` 쪽에서 갈라진다.**

```
채팅 전송 (main_window)
├─ 조회 문구면 wiki_prompt_for_query
│    └─ sync_knowledge_notes → 검색 → 발췌를 프롬프트에 넣음
│         (저장 요청이면 wants_wiki_lookup 이 꺼져 이 가지는 안 탄다)
├─ wiki_requests_go_to_hermes() == 참
│    └─ try_wiki_command / 로컬 저장  ← 가지 않음
└─ Hermes + 스킬 iris-wiki + memory nudge
     └─ MCP iris-control
          ├─ wiki.list_notes     노트마다 앞 800자 제목
          ├─ wiki.search         트리 동기화 + 임베더 프로브
          ├─ wiki.read_note      본문 최대 2만 자
          ├─ wiki.write_user_note
          │    └─ 분류기(임베딩 또는 JSON) → user/ 파일 → 위키 화면
          ├─ wiki.import_content  파일·URL 1건 (반복 호출이 생김)
          ├─ wiki.import_pages    최대 80건, 건마다 추출+분류
          ├─ wiki.move_notes / wiki.reprocess_note / open / reload
          └─ 모델이 도구를 멈춘 뒤 답
               └─ decide_followthrough
                    ├─ continue → 최대 8번, 같은 목표로 위 경로 재진입
                    └─ stop 또는 ask
```

로컬로 갔을 때의 짧은 길(지금은 채팅에서 닫혀 있음):

```
parse_wiki_command
└─ 모델이 필요 없으면 execute_wiki_command 즉시
└─ 요약·번역이면 WikiCommandWorker 한 번
     └─ 이미 작업 중이면 "이전 위키 작업이 아직 진행 중" 하고 종료
```

## 4. 코드 리뷰

### 4.1 기획대로 된 곳

| 기획 | 지금 |
|---|---|
| 장기 기억은 마크다운 1파일, 기본 쓰기는 `user/` | `~/.iris-light/iris-wiki/`. `docs/` 쓰기는 사용자 노트 API에서 거부 |
| 매 턴 볼트 전체를 넣지 않음 | 주입은 검색 상위와 글자 상한. 저장 문장은 주입을 끈다 |
| 검색 → 발췌 주입 | `wiki_prompt_for_query`. 설계 문서의 “미구현”은 옛 상태 |
| 애매하면 inbox, 폴더를 묻는다 | `ask_folder`. 키워드로 폴더를 짓지 않고, 분류 실패 시 inbox |
| 이미 있는 노트는 바이트 복사 후 원본 삭제 | `wiki.move_notes`. 본문을 다시 쓰지 말라는 스킬과 맞음 |
| 링크 `[[ ]]` 와 폴더 그래프 | `wiki_links`, 그래프 화면 |
| 비밀 형태는 검색·임베딩에서 뺀다 | `is_sensitive`. `api_key` 형태, `sk-` 긴 키, 주민번호 패턴 |
| 사이트는 같은 호스트 한 단계만 | `collect_same_origin_links`. `javascript:` `mailto:` 와 이미지·압축은 제외 |
| 세션이 끝나면 특성·에피소드 | `wiki_session`. 특성 마커 위 사용자 글은 유지, 자동 절은 12개 |

### 4.2 이상한 곳

| 지점 | 한 일 | 요청이 길어진 이유 |
|---|---|---|
| `wiki_requests_go_to_hermes` | 항상 Hermes | “저장해” 한 마디도 도구 계획부터 시작한다. 로컬 파서가 알아도 쓰지 않는다 |
| 스킬·nudge 도구 목록 | 목록·검색·읽기·쓰기·열기·여러 장 가져오기를 한 번에 안내 | 모델이 저장 전에 목록과 검색을 먼저 호출하기 쉽다. 반복 금지는 문장뿐이다 |
| `filing_kwargs` | 경로를 줬어도 분류기 연결을 먼저 연다 | 명시 경로면 분류를 안 쓰는데, Ollama 프로브와 임베더 준비는 한다 |
| `classify_note` | 임베딩으로 부모를 정한 뒤, 분야 이름만 모델 JSON | 노트 1개에 임베딩 + 최대 45초 호출. 80건이면 그 횟수만큼 |
| `wiki.search` | 호출마다 지식 파일 동기화 | 저장 루프 안의 검색이 디스크 순회를 반복한다 |
| `list_notes` | 매 호출마다 모든 `.md` 앞부분을 읽는다 | 잘린 목록(`truncated`) 뒤에서 모델이 다시 목록을 부른다 |
| `decide_followthrough` | 도구가 성공해도 “계속” 계열 마지막 문장이면 재진입 | 한 턴의 도구 반복 위에, 턴이 최대 8번 더 붙는다 |
| `wiki.import_pages` 반환 | 실패가 있어도 `ok` 로그 | 활동 줄에 ` ok ` 가 들어가 감독은 성공으로 센다. 모델은 남은 장을 또 도구로 집는다 |
| `wiki.reprocess_note` | 요약 1번 + 문단 번역 최대 24번 | 호출 한 번이 로컬 모델 수십 회. 타임아웃은 요약·번역 각 120초 |
| 설계 문서 | 2026-07-30, 자동 주입 미구현, 저장은 inbox | 코드는 분류 저장과 주입이 있다. 일지 `wiki.append_daily` 도구는 없다 |

### 4.3 예외·처리 못 할 때

| 상황 | 결과 | 그 다음 |
|---|---|---|
| 제목·본문·경로·검색어 없음 | `err_result` 문자열 | Hermes가 다른 도구로 다시 시도하기 쉽다. 사용자 문장으로 바로 끝나지 않는다 |
| 요약 모드인데 모델 없음 | `model required` | 로컬 경로만 “모델 선택이 필요”로 턴을 닫는다. Hermes 경로에는 그 한 줄 종료가 없다 |
| 분류기·임베딩 실패 | inbox, `ask_folder` | 오류가 아니다. 감독은 `ask_folder` 를 보지 않아, 모델이 다시 분류 도구를 부를 수 있다 |
| 노트가 여러 개라 경로를 모름 | 로컬은 “경로를 알려 주세요” | 채팅은 로컬을 안 타서, 모델이 목록·검색으로 고른다 |
| HWP | “아직 본문을 읽지 못합니다” | 그 한 건만 실패. 여러 장 가져오기는 다음 건을 계속한다 |
| URL에 글이 없음 | 값 오류 후 Firecrawl 시도 | 빈 페이지도 대기 시간이 붙는다. JS 위주 사이트는 스킬이 이미 “불완전”이라고 적음 |
| 번역 24문단 초과 | 남는 문단은 한국어 줄 없이 성공 | 사용자는 끝난 줄 안다. 잘렸다는 말이 없다 |
| 색인 `OSError` | 파일은 저장, 색인만 버림 | 다음 검색에 안 나온다. 모델이 다시 쓴다 |
| 옮기기 검증 실패 | `sources still present` 또는 값 오류 | 바이트가 일부 복사된 뒤 오류가 날 수 있다. 감독은 `moved` 가 아니면 다시 돌린다 |
| 이어 하기 8회 | “자동 진행 상한” 한 줄 | 여기서만 루프가 멈춘다 |
| 로컬 워커가 이미 실행 중 | “이전 위키 작업이 아직 진행 중” | 채팅 입구가 막혀 있어 Hermes 중복 호출에는 적용되지 않는다 |
| 위키 화면 갱신 예외 | 로컬 `_on_ok` 는 실패 문장으로 받는다 | Hermes 도구 안의 `show_note` 예외는 그 감싸개가 없다 |

### 4.4 보안

| 항목 | 판단 |
|---|---|
| 경로 탈출 | `..` 거부, 해석된 경로가 `user_root` 밖이면 거부. 삭제는 `user/` 만 |
| 저장소 볼트 변조 | 사용자 쓰기 API로 `docs/` 를 쓰지 못한다 |
| 검색 주입 | 비밀 정규식에 걸리면 발췌·임베딩에서 뺀다. 식이 좁다. `Bearer`, PEM, `.env` 덤프, 메일·전화는 통과한다 |
| `wiki.read_note` | 비밀 검사를 하지 않는다. 경로를 알면 본문 2만 자가 도구 결과로 나간다 |
| URL 가져오기 | `http`/`https` 만 URL로 본다. `file://` 은 URL이 아니다. 사설 IP·링크 로컬·리다이렉트·클라우드 메타데이터 주소는 막지 않는다 |
| 본문 크기 | 링크 수집용 HTML 은 200만 바이트에서 자른다. 본문 추출 `resp.read()` 는 상한이 없다 |
| 로컬 파일 | `content.extract` / `import_content` 의 `source` 가 디스크에 있으면 위키 밖 파일도 읽는다. 작업 폴더 밖 금지는 없다 |
| 프로필 | 이름·연락처·메일이 `profile/profile.md` 평문이다. 비밀번호는 노트에 안 넣고 DB 암호문이라고 적어 두었다 |
| 세션 요약 | 대화 끝을 로컬 모델에 넘겨 `profile/traits.md` 에 붙인다. 비밀 정규식에 걸리면 그 절은 거절한다 |

## 5. 개선안

빈자리만 적는다.

1. **한 방 입구.** 명령 파서가 한 동작으로 끝나면 Hermes 도구 고리를 열지 않는다. 지금 그 함수는 채팅에서 막혀 있다.
2. **분류기 지연.** 사용자가 경로를 줬고 그 경로가 inbox가 아니면 `open_classifier` 를 호출하지 않는다.
3. **감독 조건.** 이번 턴에 쓰기·가져오기·옮기기 `ok` 가 있으면 멈춘다. 다시 돌리는 경우는 `import_pages` 가 `truncated` 이거나, 옮긴 뒤 `left` 가 남은 때뿐이다. “계속할까요” 한 문장으로 턴을 이어 가지 않는다.
4. **같은 턴 반복.** `import_content` 가 두 번째면 오류로 “`wiki.import_pages` 한 번”을 반환한다. 스킬 문장에만 두지 않는다.
5. **실패를 성공으로 세지 않기.** `saved=0` 이거나 `failed>0` 이면 활동 줄을 `ok` 로 찍지 않는다.
6. **읽기 가드.** `read_note` 도 `is_sensitive` 이면 본문 대신 거절한다. URL 은 사설·링크 로컬로 붙기 전에 끊고, `read` 에 바이트 상한을 둔다.
7. **가져오기 경로.** 위키로 넣는 로컬 파일은 사용자가 고른 경로·첨부·열린 프로젝트 안으로 제한한다.

## 6. 차용

| 이름 | 가져올 부분 | 이번에 가져오지 않는 이유 |
|---|---|---|
| 스킬 `iris-wiki` (이미 설치) | “페이지마다 `import_content` 를 반복하지 말 것” | 문장만 있고 도구가 말을 안 듣는다. 스킬을 더 늘리면 도구 목록만 길어진다 |
| MCP `iris-control` (이미 연결) | `wiki.*` 호출 자체 | 도구는 충분하다. 부족한 것은 호출 횟수 제한이다 |
| Python `ipaddress` (표준 라이브러리) | URL을 열기 전에 사설·루프백·링크로컬 판별 | 새 꾸러미가 필요 없다. 아직 `fetch_url_text` 에 없다 |
| Karpathy llm-wiki 흐름 (설계 문서가 이미 가리킴) | 넣기(ingest)와 묻기(query)를 채팅 도구 고리 밖으로 나누기 | 저장소를 들여올 필요가 없다. 빈자리는 5절 1·4번이다 |
| 에이전트 SDK의 max turns 패턴 | “도구 N회 또는 목표 달성 시 정지” | SDK를 붙이지 않는다. `CAP=8` 은 이미 있다. 정지 조건이 넓다 |
| 그 외 루프 차단 라이브러리 | — | 찾지 못함. 한글 목표 문장으로 턴을 다시 여는 부분은 이 저장소 규칙이다 |

## 7. 하지 않은 일

그래프 화면, 일정·메일 노트 동기화, IDE 프로젝트 로그는 이번 채팅 도구 반복의 입구가 아니다. 손대지 않았다.

`settle_wiki_claim` 이 답을 통째로 바꾸던 동작은 현재 함수에 없다. 받은 문장을 그대로 둔다.

## 8. 조치

1. 구현은 5절 순서대로. 1번(한 방 입구)과 3번(감독이 성공 후 멈춤)이 체감 지연의 대부분이다.
2. 고친 뒤 `python -m iris.ui.wiki_turn`, `python -m iris.runtime.turn_followthrough`, `python -m iris.knowledge._check_wiki_filing` 을 돌린다.
3. 설계 문서 상태 줄은 코드와 맞춘 뒤에만 고친다. 이번 보고서의 구현 범위가 아니다.
