# 다중 채팅 동시 작업 3단계 착수 검토

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-REV-2026-1012-02 |
| 작성일 | 2026-10-12 |
| 관련 | IRIS-REV-2026-1012-01, IRIS-IMPL-2026-1011-01, IRIS-REV-2026-0930-02 |
| 대상 | Iris Light 메인 채팅. 3단계 착수 여부 |
| 목적 | 2단계 완료 기준이 소스에 있는지 보고, worktree를 열어도 되는지 가른다 |

대조 기준은 2026-10-12 분석 보고서와 구현 보고서의 3단계 정의다. 세션 헤더를 완료 요청에 넣는 기준은 분석 보고서가 철회했다. 오늘 `backend_call._hermes`가 `set_inference_model`을 멈추고 `provider`를 싣는 수정이 들어갔다. 같은 날 `tests.test_request_model`, `tests.test_handoff_summary_worker`, `tests.test_hermes_model_failover` 25건, `python -m iris.ui._check_conversation_switch_cancel`, `python -m iris.ui._check_turn_followup`이 통과했다.

---

## 1. 결론

3단계로 넘어가도 된다. 2단계가 맡기로 한 바인딩과 요청 단위 모델은 소스에 있다. 제목·루틴·인수인계도 게이트웨이 설정 칸을 덮지 않는다.

3단계가 여는 것은 같은 저장소를 동시에 고칠 때의 폴더 사본뿐이다. 업스트림 주소와 키는 설정 한 칸으로 남아 있고, worktree는 그 칸을 나누지 않는다. 그 칸이 남았다는 이유로 3단계를 막지 않는다. 3단계 완료로 그 칸이 갈라졌다고 보지도 않는다.

---

## 2. 구조

```text
착수 판단
  └─ 2단계 완료 (세션 헤더는 철회된 기준)
       ├─ choose_turn_model → 슬롯의 런타임 id
       ├─ HermesChatWorker.run → set_inference_model 없음, provider 있음
       ├─ backend_call._hermes → set_inference_model 없음, provider 있음
       └─ 주소·키는 HermesModelSyncWorker 가 쓰는 설정 한 칸   ← 3단계가 안 닫는 곳
            └─ 3단계 자리 (코드 없음)
                 └─ profile.project_root 하나
                      ├─ _current_project_root / ide.set_project_root
                      ├─ _ide_session 하나
                      └─ SessionWriteLock 프로젝트 잠금 하나
                           └─ git worktree add 없음
```

갈라지는 지점은 채팅 둘의 파일 쓰기가 같은 `project_root`와 잠금 하나를 보는 곳이다. 모델 이름 분리는 그 위에 이미 있다.

## 3. 코드 리뷰

| 기준 | 판정 | 근거 |
|---|---|---|
| 슬롯이 런타임 id를 기억한다. 이어하기는 피커를 부르지 않는다 | 충족 | `choose_turn_model`. `inference_model` 기본값은 빈 문자열 |
| 메인 채팅 `HermesChatWorker.run`이 `set_inference_model`을 호출하지 않는다 | 충족 | `run`은 `stream_chat(stream_model, provider=)`만 호출한다 |
| `provider`가 있으면 광고 이름이 하나여도 업스트림 이름을 유지한다 | 충족 | 채팅 워커와 `backend_call._hermes`가 타깃의 `provider`를 넘긴다 |
| 완료 페이로드의 `model`은 업스트림 이름이다 | 충족 | `stream_model = target.model` |
| 페이로드에 `api_key`와 `X-Hermes-Session-Id`가 없다 | 충족 | `hermes_client.py`에 세션 헤더 문자열이 없다. 분석 보고서가 헤더 없음을 미완료에서 뺐다 |
| 화면을 옮긴 뒤의 기록은 그 턴의 대화에 남는다. 전환은 워커를 취소하지 않는다 | 충족 | `_load_conversation`은 화면과 구체만 바꾼다. `CAP = 8`, `MAX_CONCURRENT = 10` |
| 같은 저장소를 고치는 채팅이 폴더를 나눈다 | 비어 있음 | `iris/`에 `worktree` 호출이 없다. 루트는 `profile.project_root` 하나다 |

충족 경로에서 하지 않은 일. 헤르메스 소스 수정, `direct_model_requests`, Sessions API, 메일 패널의 `ChatRunMap` 흡수, Git worktree.

`inference_provider`는 발사 때 한 번 저장한다. 다음 턴은 그 필드를 읽지 않고 `resolve_hermes_inference`를 다시 탄다. 그 사이에 API 행이 바뀌면 이어하기의 주소도 바뀐다.

설정 칸을 아직 쓰는 호출.

| 호출 | 하는 일 |
|---|---|
| `HermesModelSyncWorker` | 피커·게이트웨이 접속이 `set_inference_model`로 주소와 키를 쓴다 |
| `hermes_ollama_guard.note_after_provider_direct_ok` | 접속 확인이 같은 쓰기를 한 번 한다 |

예전 1단계 잔여 가운데 지금 소스에서 좁혀진 것. 채팅 삭제는 `_cancel_slot_for_delete`가 그 대화의 워커와 `clear_pending_for`만 끊는다. 마이크 정지는 `stt_queue.clear_pending`만 부른다. 턴 디스패처의 전체 `clear_pending`은 앱 경로에서 호출되지 않는다. 잠금 표에는 `ide.open_folder`, `project.create_scaffold`, `wiki.move_notes`, `note.export_pdf`가 있다.

아직 표 밖인 쓰기. `ide.open_file`, `ide.marketplace_install`, `ide.set_project_root`. `acquire_project`와 `acquire_wiki`는 타임아웃이 없다. 이 자리는 3단계와 한 묶음이 아니다.

---

## 4. 개선안

3단계가 메울 빈 자리.

1. 같은 저장소를 고치는 채팅이 `git worktree add`로 폴더를 나누는 자리. 그 채팅의 IDE와 터미널만 그 폴더를 본다.
2. 본 트리로 들이는 변경은 사용자가 확인한 뒤뿐인 자리. 자동 병합은 없다. 위키 노트로 사본을 만들지 않는다.

3단계가 메우지 않는 자리. 게이트웨이 설정의 주소·키 한 칸. 세션 헤더. 잠금 대기 시간. 표 밖 IDE 액션.

---

## 5. 차용

| 이름 | 가져올 부분 | 이번에 가져오지 않는 이유 |
|---|---|---|
| `git worktree add` | 채팅마다 작업 폴더를 나눔 | 아직 호출이 없음. 3단계가 이 명령만 연다 |
| 본 트리 반영 | 사용자가 확인한 변경만 | 자동 병합·자동 삭제는 명세가 빼 둠 |
| `X-Hermes-Session-Id` | 없음 | 본문 이전 턴을 `state.db`로 바꾸므로 넣지 않음 |
| 요청 본문의 `base_url`·`api_key` | 없음 | 주소 칸을 worktree로 나누지 않음. 키를 로그에 싣지 않음 |
| 잠금 타임아웃·표 밖 IDE | 없음 | 분석 보고서가 이 수정과 한 묶음으로 넣지 말라고 함 |

---

## 6. 조치

1. 3단계 구현은 같은 저장소를 동시에 고칠 때의 worktree만 담는다.
2. 주소·키 한 칸, 세션 헤더, 잠금 대기, 표 밖 IDE 액션은 그 구현에 넣지 않는다.
3. 본 트리 반영은 사용자 확인 뒤로 둔다. 자동 병합은 넣지 않는다.
