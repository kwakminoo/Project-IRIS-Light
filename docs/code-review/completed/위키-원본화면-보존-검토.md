# 위키 원본 화면 보존 검토

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-CR-2026-1008-WIKI-VIS |
| 작성일 | 2026-10-08 |
| 관련 | `iris/knowledge/content_extract.py`, `wiki_summarize.py`, `wiki_ops.py`, `iris/ui/workspaces/obsidian_workspace_page.py` |
| 대상 | PDF·웹페이지를 위키에 넣을 때의 저장량, 요약, 화면 |
| 목적 | 지금 저장 방식을 확정하고, 위에 요약·아래에 원본 화면을 둘지와 그 방법을 정한다 |

## 1. 결론

지금 위키는 PDF와 웹페이지의 **글자만** 마크다운으로 남긴다. 표·그림·단 배치·글자가 없는 쪽은 저장되지 않는다. 위키 창은 `QTextBrowser`라 크롬에서 연 화면을 그리지 못한다.

위에 지금과 같은 요약, 아래에 원본 화면을 두는 구성은 하는 편이 맞다. 방법은 종류별로 나눈다.

| 자료 | 저장 | 위키에서 보는 법 |
|---|---|---|
| PDF | 원본 PDF 파일을 노트 옆에 복사 | 이미 있는 Chromium(`QWebEngineView`) PDF 보기로 연다. 크롬에서 PDF를 연 것과 같다. 창 너비에 맞춘다. |
| 웹페이지 | 글·그림·스타일을 한 HTML 파일로 고정 | 같은 Chromium으로 연다. 위키 창 너비에 맞춰 다시 배치된다. |

페이지를 캡처해 이어 붙이는 방식은 기본으로 두지 않는다. 글자 선택·검색·용량에서 진다. 캔버스처럼 HTML로 못 받는 페이지만 이미지로 남긴다.

글자 추출과 요약은 유지한다. 화면 파일만 있으면 위키 검색이 글자를 못 찾는다.

## 2. 지금 저장되는 양

위키에 쓰는 파일은 `user/…​.md` 하나다. 본문 상한은 **8만 자**다. 넘으면 줄 경계에서 자르고 `truncated`를 붙인다. 채팅에 자료를 붙일 때와 위키 저장은 상한이 다르다.

| 쓰임 | 상한 | 위치 |
|---|---|---|
| 위키 본문 | 8만 자. PDF는 쪽 제한 없음 | `content_extract._MAX_CHARS`, `extract_from_source` |
| 채팅에 넣는 발췌 | 1만 2천 자. PDF는 앞 8쪽 | `material_excerpt.CHAT_EXCERPT_CHARS`, `CHAT_PDF_PAGES` |
| 요약에 넣는 글 | 앞 2만 4천 자 | `wiki_summarize.summarize_for_wiki` |
| 문단 번역 | 문단 24개, 문단당 4천 자 | `wiki_ops._MAX_TRANSLATE_CALLS`, `translate_for_wiki` |
| 검색에 보여주는 발췌 | 800자 | `wiki_note_index._EXCERPT` |
| 이미지 PDF를 비전으로 읽는 쪽 | 최대 4쪽 | `content_extract.VISION_PAGE_CAP` |

채팅 발췌와, 답변을 PDF 파일로 **내보내는** `pdf_job`(20만 자)은 위키 원본 보관이 아니다.

### PDF

1. `pypdf`로 쪽마다 글자 층을 읽는다.
2. 숫자·영문·한글이 40자 미만이면 `pymupdf`가 130dpi PNG를 만들고 Tesseract(`kor+eng`)로 OCR한다. PNG는 버린다.
3. OCR 글자가 8자 미만이고 비전 함수가 있으면, 그 PNG를 최대 4장까지 모델에 보내 받아 적는다.
4. 본문이 비면 저장하지 않는다. 암호 PDF는 거부한다.

### 웹페이지

1. `urllib`로 HTML을 받는다. 자바스크립트는 실행하지 않는다.
2. `trafilatura`가 본문을 주면 그 글을 쓴다. 없으면 `script`·`style`·메뉴·머리·바닥을 뺀 표준 파서가 글자만 모은다.
3. 본문이 비고 `FIRECRAWL_API_KEY`가 있으면 Firecrawl에 **마크다운**만 요청한다. 화면은 요청하지 않는다.

저장 형식은 제목, `- source:`, 본문, `> updated:` 시각이다 (`IrisWiki.write_inbox_note`).

### 요약이 붙는 조건

「저장」만 하면 추출 글이 그대로 들어간다. 요약 문장이 있을 때만 모델이 돈다.

| 사용자 말 | 노트 내용 |
|---|---|
| 저장 (요약·원문 단어 없음) | 추출 글 전체 (8만 자까지) |
| 요약·정리·핵심·개요 + 원문 유지가 기본 | `## 정리` 다음에 `## 원문` (문단 글) |
| 요약만, 원문 빼기 | 요약만. 추출 글은 노트에 없음 |

요약 지시문은 한국어 마크다운, 불릿, 필요하면 인용, 짧은 결론이다. 모델은 Ollama 단발이고 이미지는 보내지 않는다. 요약 입력이 2만 4천 자에서 끊기므로, 긴 PDF의 뒷부분은 요약에 안 들어간다.

위키 화면은 `ObsidianWorkspacePage`의 `QTextBrowser`다. `render_wiki_document`가 마크다운을 Qt 리치텍스트 HTML로 바꾼다. 크롬 레이아웃, PDF, iframe은 그리지 않는다.

## 3. 구조

```
채팅 「이 PDF/URL 위키에 저장」
  wiki_command.parse_wiki_command
    ├─ 요약·번역 없음 → wiki_import_ops.import_to_wiki (mode=raw)
    ├─ 요약 + 원문 유지 → prepare_wiki_body → compose_reprocessed
    └─ 요약만 → import_to_wiki (mode=summarize)
         extract_from_source
           ├─ URL → fetch_url_text → html_to_article (trafilatura / 표준 파서)
           │         실패 시 fetch_firecrawl_text (markdown)
           └─ PDF → read_pdf_pages (글자 층 → OCR PNG 폐기 → 비전 4쪽)
         _truncate (8만 자)
         summarize_for_wiki (앞 2만 4천 자, 요약 모드일 때만)
         file_user_note → write_inbox_note (*.md)
         wiki_note_index (본문 색인, 검색 발췌 800자)
위키 창
  obsidian_workspace_page.show_note
    render_wiki_document → QTextBrowser.setHtml
```

이번 요청(화면을 그대로 보기)은 `extract_from_source`에서 갈라진다. 여기서 PNG·HTML을 버리고 글자만 넘긴다. 위키 창은 그 글의 마크다운만 그린다.

## 4. 코드 리뷰

| 지점 | 이번 증상에서 한 일 | 화면이 안 남는 이유 |
|---|---|---|
| `extract_from_source` | URL·PDF를 `{kind, title, text}`로만 반환 | 반환에 파일 바이트·HTML·이미지가 없다 |
| `read_pdf_pages` | 글자 층, 부족하면 OCR, 그래도 부족하면 비전 4쪽 | `_page_png` 결과는 OCR·비전 입력으로만 쓰고 폐기 |
| `fetch_url_text` | JS 없이 HTML에서 본문 글만 추출 | 메뉴·스타일·그림을 빼고, SPA는 빈 껍데기만 받는다 |
| `fetch_firecrawl_text` | 마크다운 폴백 | `formats: ["markdown"]`만 요청 |
| `summarize_for_wiki` | 앞 2만 4천 자를 한국어 불릿으로 요약 | 입력이 이미 글자뿐이다 |
| `compose_reprocessed` | `## 정리` + `## 원문` 문단 | 원문이 추출 텍스트다 |
| `write_inbox_note` | `.md` 한 파일 | 첨부 디렉터리가 없다 |
| `render_wiki_document` + `QTextBrowser` | 마크다운 미리보기 | Qt 리치텍스트는 CSS·PDF를 크롬처럼 그리지 못한다 |
| `email_workspace_page._ensure_body_view` | 메일 HTML을 Chromium으로 표시 | 위키 미리보기는 이 경로를 쓰지 않는다 |

하지 않은 일: `pdf_job` / `pdf_export`는 채팅·자료를 PDF로 **만드는** 길이다. `material_excerpt`는 채팅 프롬프트용 짧은 발췌다. `page_vision.transcribe_images`는 글자로 옮길 뿐 이미지를 노트에 붙이지 않는다.

## 5. 개선안

노트는 지금처럼 글과 요약을 두고, 원본 파일만 옆에 둔다.

```
user/<폴더>/<slug>.md
user/<폴더>/<slug>.assets/original.pdf | original.html
```

`.md` 본문:

```markdown
# 제목
- source: …

## 정리
(지금 summarize_for_wiki 결과. 요약 요청이 없으면 이 절은 생략)

## 원본
(뷰어가 열 파일 표시. 본문 글은 검색용으로 유지)
```

위키 창은 위를 지금 `QTextBrowser`, 아래를 노트를 열 때 만드는 `QWebEngineView`로 나눈다. 메일 화면과 같이 생성은 첫 사용까지 미룬다. `MainWindow` 생성 중에 만들면 기동이 멈춘다 (`qt_bootstrap`).

| 방법 | 판단 |
|---|---|
| PDF를 Chromium PDF 보기로 열기 | 채택. 크롬과 같은 엔진이다. 글자 선택·확대·너비 맞춤이 된다. 래스터라이즈가 필요 없다. |
| 웹을 단일 HTML로 저장한 뒤 Chromium으로 열기 | 채택. 위키 창 너비에 맞춰 다시 배치된다. 오프라인으로 남는다. |
| 웹을 `printToPdf`로 PDF화 | 보조. 캡처 순간 화면은 남지만 종이 너비에 고정된다. 창을 줄여도 사이트가 다시 흐르지 않는다. |
| 전체 페이지 캡처를 이어 붙이기 | 폴백. 글자 선택이 안 되고 길면 용량이 크다. HTML로 못 받는 경우만. |
| 받은 HTML을 지금 `QTextBrowser`에 넣기 | 기각. 메일 HTML을 Chromium으로 옮긴 이유와 같다. Qt 리치텍스트는 사이트 CSS를 그리지 못한다. |
| 저장 없이 URL을 그 자리에서 열기 | 기각. 화면은 맞지만 페이지가 바뀌면 위키 기록이 바뀐다. 로그인 페이지는 나중에 빈 화면이 된다. |

자바스크립트가 그린 사이트는 지금 `urllib` 경로로는 본문이 비는 경우가 있다. 화면 저장은 로드가 끝난 Chromium에서 해야 한다.

저장 HTML의 스크립트는 끈다. 로컬 파일을 읽는 페이지가 위키 폴더 밖으로 나가지 않게 한다. PDF 보기는 페이지 스크립트가 필요 없다.

8만 자 상한은 **검색용 글**에만 둔다. 화면 파일은 그 상한으로 자르지 않는다.

## 6. 차용

| 이름 | 가져올 부분 | 이번에 가져오지 않는 이유 |
|---|---|---|
| PyQt6-WebEngine 6.11 (이미 설치) | PDF 플러그인, HTML 렌더 | — |
| `email_workspace_page._ensure_body_view` | 첫 열람 때 `QWebEngineView` 생성 | — |
| `pymupdf` `get_pixmap` (이미 OCR에 사용) | 쪽 이미지 | 표시용으로 쓰면 캡처 폴백과 같다. OCR 입력으로만 유지 |
| trafilatura (이미 사용) | 요약·검색용 본문 글 | 화면 보존 용도가 아니다 |
| Firecrawl screenshot 포맷 | 없음 | 유료 API이고 결과도 래스터다. 기본 경로로 두지 않는다 |
| monolith 또는 SingleFile 방식 | CSS·이미지를 한 HTML에 넣는 절차 | 앱에 없다. 웹 저장을 구현할 때 이 절차만 가져온다. 뷰어를 새로 만들지 않는다 |
| pdf.js, Qt Pdf `QPdfView` | 없음 | WebEngine PDF 보기와 겹친다 |
| Playwright | 없음 | 캡처용 브라우저가 이미 `QWebEngine`으로 있다 |

## 7. 조치

1. 구현함. 위키 저장은 항상 `## 전체 요약`, `## 핵심 개념`, `## 원본` 순이다.
2. PDF는 노트 옆 `*.assets/original.pdf`, 웹·HTML은 스타일과 그림을 넣은 `original.html`이다. 위키 창은 위를 요약, 아래를 Chromium으로 연다.
3. 위키로 넣을 때 글자 상한은 없다. 글자 층·OCR이 비는 쪽은 개수를 세고 한 장씩 읽는다. 검색 발췌 800자는 검색 표시용으로 그대로다.
