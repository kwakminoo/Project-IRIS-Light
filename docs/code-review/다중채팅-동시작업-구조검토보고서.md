## 1. 결론

지금 구조로는 불가능하다. 대화 기록은 채팅마다 저장되지만, 모델 호출과 도구 실행은 창 전체에서 하나다. 다른 채팅을 열면 진행 중 작업이 취소된다.

목표 동작은 가능하다. 공통 패턴은 「채팅 하나 = 세션 하나 = 그 세션 안의 도구 루프」이다. 파일을 고치는 작업은 세션만 나누면 부족하고, 작업 사본(Git worktree 또는 동등한 격리)이 있어야 서로 덮어쓰지 않는다. 글 조사·위키 요약처럼 서로 다른 대상을 읽는 작업은 세션 분리만으로 병렬이 된다.

권고는 한 번에 전면 교체하지 않고, 세션 실행을 먼저 나누고, 파일·IDE 쓰기는 잠금 또는 worktree로 나중에 여는 것이다.

**세션.** 세션은 「이 채팅이 아직 일을 끝내지 않았다」는 작업 단위다. 노트(대화 기록), 진행 표시(바쁨, 이어하기 횟수, 아직 다 오지 않은 답), 루프(모델이 생각하고, 도구를 부르고, 결과를 보고, 다시 생각하는 반복)가 그 채팅에만 붙어 있다. 상황으로 보면, 채팅 A가 위키 페이지를 여럿 저장하는 도중에도 채팅 B에서 다른 질문을 보낼 수 있는 상태다. A의 루프는 B 화면 뒤에서 계속 돈다.

코드의 `ChatSession`은 아직 노트만 담당한다. 대화 id와 DB 히스토리다. 이 보고서의 세션은 거기에 워커와 루프를 붙인 것이다.

제품 화면의 「채팅을 여러 개 연다」는 위 모델의 결과다. GPT·Claude 앱의 채팅은 서로 다른 대화 상태이고, Cursor의 병렬 코딩은 그 위에 파일 격리를 얹은 것이다. 내부 큐 구현의 소스은 공개되어 있지 않다.

**이 구조들을 가져오면 장애가 사라지나.** 사라지는 것은 아이리스의 구조 장애다. 채팅을 옮기면 작업이 취소되는 것, 실행 슬롯이 하나인 것, 모델 설정이 창 전체인 것, 두 채팅이 같은 파일을 같이 고치는 것, 도구 기록이 창 하나에 섞이는 것이다. OpenAI의 conversation은 채팅마다 기록을 잇는 방식이고, Cursor 서브에이전트는 부모 화면을 막지 않는 뒤 루프이며, 체인 로그는 그 채팅의 도구 호출 기록이다. Git worktree는 코딩할 때만 폴더를 나눈다.

그대로 남는 것은 자원과 사람의 한계다. GPU가 요청을 줄 세우는 것, 마이크가 하나인 것, 승인 창이 화면을 가리는 것, 나뉜 코드 사본을 다시 합치는 일이다. 위 제품의 화면을 설치하면 해결되는 종류가 아니다. 아이리스가 그 패턴으로 세션을 나누면 해결되는 종류다.

## 3. 현재 Iris

메인 채팅은 창 하나, 실행 슬롯 하나다.


| 구성  | 현재                                                                              |
| --- | ------------------------------------------------------------------------------- |
| 기록  | `ChatSession`이 대화 id와 히스토리를 DB에 나눈다. 이 부분은 이미 채팅별이다.                            |
| 실행  | `ChatTurnGate.busy`, `UserTurnDispatcher`, `_chat_worker`가 각 하나다.               |
| 전환  | `_load_conversation`은 생성 중이면 `request_cancel`하고 `대화 전환으로 응답을 중단했습니다.`를 남긴다.     |
| 입력  | 생성 중 전송 버튼은 정지다. 키보드 전송은 대화 id를 큐에 싣지 않는다.                                      |
| 모델  | `settings.ollama_model`이 하나다. Hermes `set_inference_model`은 런타임 기본 모델을 통째로 바꾼다. |
| 도구  | IDE, 파일 쓰기, 위키, 긴 작업 이어하기가 창 전역 상태다.                                            |
| 예외  | 메일·캘린더 패널은 워커가 따로 있으나, 채팅 목록의 다른 대화가 아니다. 그 화면일 때 메인 턴을 끝내고 넘긴다.                |


그래서 자료 조사 중이어도 다른 채팅의 IDE 작업이 그 조사를 끊는다. 저장이 나뉜 것과 실행이 나뉜 것은 다르다.

**위키와의 관계.** 채팅 글은 이미 위키로 들어간다. 프로젝트는 `projects/<슬러그>/`, 그 안의 채팅 원문은 `chats/<대화 id>.md`, 떠날 때 묶음은 에피소드다. 위키는 그 글의 보관 위치다. 워커나 루프가 아니다. 한 프로젝트 위키 안에 채팅이 여러 개다. 루프를 위키 단위로 묶으면, 같은 프로젝트의 채팅들이 다시 실행 슬롯 하나를 나눠 쓴다. 분리 단위는 위키가 아니라 채팅(대화 id)이다.

## 4. 목표 구조

채팅은 세션이다. 세션은 자기 기록, 자기 모델, 자기 도구 루프를 가진다. 화면은 그중 하나만 크게 보여주고, 나머지는 백그라운드에서 같은 루프를 돈다.

```text
채팅 A ── 세션 A ── 루프(모델, 도구, 기록 A)
채팅 B ── 세션 B ── 루프(모델, 도구, 기록 B)
화면은 포그라운드 세션만 그린다.
파일 쓰기는 세션이 빌린 작업 사본 또는 경로 잠금 안에서만 한다.
```

도구 종류별 격리:


| 작업                     | 필요한 격리                              |
| ---------------------- | ----------------------------------- |
| 대화, 자료 조사, 서로 다른 문서 읽기 | 세션 기록과 루프만 분리                       |
| 위키에 서로 다른 노트 쓰기        | 경로 잠금. 같은 노트는 한 세션만                 |
| IDE, 같은 저장소 수정         | Git worktree 또는 동등한 사본. 본 트리는 한 세션만 |
| 터미널 명령                 | 세션별 작업 디렉터리. 같은 디렉터리의 동시 실행은 금지     |


Cursor 공개 문서의 worktree, OpenAI의 conversation id, Claude의 session/thread가 같은 역할이다. ReAct 논문의 궤적은 세션 안에 있고, 궤적끼리 합치지 않는다.

**위키로 세션과 worktree를 대신할 수 있나.** 세션은 대신할 수 있다. 다만 키는 위키 폴더가 아니라 그 안의 채팅이다. 채팅마다 루프를 두면, 끝난 글이 위키에 저장되는 지금의 흐름과 맞다. 서로 다른 노트를 읽고 쓰는 조사는 이 분리만으로 병렬이 된다. 같은 노트는 아래 5항의 경로 잠금으로 한 채팅만 쓴다.

코딩용 worktree는 위키가 대신하지 못한다. 위키 페이지는 마크다운 노트다. IDE가 고치는 것은 그 노트가 아니라 프로젝트 소스, 빌드, 터미널의 작업 폴더다. 채팅 원문이 `chats/<id>.md`로 이미 파일마다 나뉘어 있는 것과, `main.py` 작업 폴더를 두 개 두는 것은 다른 일이다. 조사·위키 쓰기는 세션과 경로 잠금, 같은 저장소 수정은 worktree다.

## 5. Iris 수정 순서

1. **세션 실행 객체.** 대화 id마다 워커, 진행 플래그, 이어하기 횟수, 부분 응답을 둔다. `ChatTurnGate`와 `_chat_worker` 단일 필드를 맵으로 바꾼다. 지금 보고 있지 않은 세션의 토큰은 그 대화 DB에만 붙인다.

   **이어하기 횟수.** 페이지를 전부 저장하는 것처럼 긴 일에서, 모델이 말을 끊어도 일이 남아 있으면 아이리스가 같은 목표로 다음 턴을 스스로 보낸다. 그 보낸 횟수가 `_followthrough_count`다. `turn_followthrough.CAP`은 8이다. 8이 되면 「자동 진행 상한에 도달했습니다. 이어서 하려면 다시 요청하세요.」를 남기고 멈춘다. 지금 이 숫자는 창에 하나다. 채팅을 옮기면 `_drop_followthrough`가 0으로 지운다. 세션으로 나누면 채팅 A의 6회가 채팅 B의 상한으로 세지거나, 화면을 옮겼다고 A의 남은 횟수가 사라지면 안 된다. 그래서 워커와 함께 대화 id마다 둔다.

   **8인 이유.** 8은 모델 능력이나 원격·로컬과 무관한 안전 브레이크다. 근거 문서는 `docs/code-review/completed/긴작업-일괄저장과-턴감독-구현프롬프트.md`다. 사이트 전체 저장 시험에서 모델이 몇 페이지만 저장하고 「계속할까요」로 턴을 닫았다. 아이리스는 그 문장을 완료로 기록했다. 그래서 목표가 남아 있고 도구 증거가 부족하면, 사용자 입력 없이 다음 턴을 넣게 했다. 그 계약에 `cap: int = 8`을 넣었고, 검사도 `followups==8`이면 멈추게 고정했다. 측정해서 8이 최적이라고 정한 값은 아니다.

   상한을 없애면 그 자동 루프가 모델의 말버릇에 묶인다. 「이어서 진행하겠습니다」「저장했습니다」를 반복하는데 도구는 끝나지 않은 경우, 턴이 요금과 파일 쓰기를 계속 소비한다. 정상 완료는 상한 전에 멈춘다. 「67건 저장, 0건 실패」나 폴더 이동이 끝나면 `decide_followthrough`가 stop이다. 8은 그 증거가 안 나올 때만 닿는다. 상한 뒤에도 사용자가 다시 요청하면 횟수는 0부터다. 숫자를 늘리는 것은 가능하고, 자동 턴에서 상한 자체를 빼는 것은 멈춤 버튼을 누르기 전까지의 무한 재호출이 된다.

   **단일 필드를 맵으로.** 지금은 `self._chat_worker` 변수 하나, `ChatTurnGate.busy` 참/거짓 하나다. 채팅을 바꿔도 그 칸을 비우고 다음 채팅이 들어간다. 맵은 대화 id를 키로 한 사전이다. 12번 채팅의 워커와 15번 채팅의 워커가 동시에 들어 있다. `busy`도 채팅마다 따로다.

2. **전환은 화면만 바꾼다.** `_load_conversation`에서 `conversation_switch` 취소를 뺀다. 포그라운드가 바뀌어도 백그라운드 루프는 `request_cancel`하지 않는다.

   **구체.** 구체는 창에 하나다. 창 상태(`AppState`)를 그린다. 지금은 다른 채팅으로 옮기면 진행 중 턴을 취소하므로, 작업도 멈추고 구체도 쉰다. 이 항을 적용한 뒤의 화면은 이렇게 간다. 채팅 A가 생성 중이면 A를 보고 있는 동안 구체가 돈다. B로 옮기면 B가 쉬고 있으므로 구체는 B 기준으로 쉰다. A의 루프는 뒤에서 계속 토큰을 A의 기록에 붙인다. A로 돌아오면 A가 아직 생성이면 구체가 다시 돈다. 떠난 동안 A가 끝났으면 글은 채워져 있고 구체는 쉰다. 작업이 멈춘 것이 아니라, 구체가 지금 보이는 채팅만 따라간다.

3. **입력은 세션으로 보낸다.** 키보드 전송에 대화 id를 싣는다. 생성 중인 채팅의 버튼은 그 채팅의 정지이고, 다른 채팅의 전송을 막지 않는다.
4. **모델은 요청 단위.** Hermes가 켜져 있으면 `set_inference_model`로 전역 기본 모델을 바꾸지 않고, 그 요청의 모델만 싣는다. 같은 모델만 병렬로 쓸 1단계에서는 이 항을 미룰 수 있다. 헤르메스 쪽 의미는 8절에 있다.
5. **쓰기 도구는 빌림.** IDE·`project.write_file`·터미널은 세션이 잠금을 얻었을 때만 실행한다. 잠금이 없으면 그 세션은 기다리고, 다른 세션의 읽기·조사는 계속된다. worktree는 그 다음 단계다.

   **빌림과 잠금.** 도구 프로그램을 복사해 가는 뜻이 아니다. 「지금 이 파일(또는 IDE, 이 터미널 폴더)을 고치는 채팅은 나」라는 표식을 먼저 집는 것이다. 그 표식이 잠금이다. 채팅 A가 `main.py` 잠금을 쥐고 있으면, 채팅 B의 같은 파일 쓰기는 B 안에서만 기다린다. B의 글 조사와 다른 노트 읽기는 그 대기와 상관없이 진행된다. A가 잠금을 놓으면 B가 이어서 쓴다. 1·2단계의 코딩은 그래서 한 채팅만 쓴다.

6. **상한.** 동시 루프는 2 또는 3으로 시작한다. 로컬 Ollama는 한 모델 서버를 나눠 쓰므로 무제한 병렬은 처리량만 떨어뜨린다. 아래 설명대로, 평소 경로가 원격 API이면 이 시작값의 이유는 GPU가 아니다.

   **한 모델로 병렬이 되나.** 된다. 원격 API(NVIDIA, Gemini 등)는 모델 이름이 하나여도 서버가 요청을 여러 건 동시에 받는다. 막히는 곳은 모델이 아니라 아이리스의 실행 슬롯 하나다. 세션을 나누면 같은 모델로 채팅 여러 개의 루프가 동시에 간다. 로컬 Ollama는 연구·특수 상황에서만 쓰면, 「GPU가 직렬이라 병렬이 불가능하다」는 평소 경로의 이유가 아니다.

   남는 상한은 세 가지다. 헤르메스 게이트웨이 기본 동시 실행은 10이고, 넘으면 HTTP 429다. 제공자 계정의 분당·동시 요청 한도와 요금이 있다. 파일 쓰기는 모델이 병렬이어도 잠금이 필요하다. 2 또는 3은 그 한도 안의 시작값이고, 승인 창이 보고 있는 화면을 가리는 문제(6절)에 맞춘 것이다. 처리와 화면이 감당되면 올린다. 모델을 채팅마다 다르게 고르지 않아도 된다. 채팅마다 다른 모델은 2단계이고, 1단계의 조건이 아니다.

메일·캘린더 패널의 별도 워커는 이 세션 맵에 흡수할 대상이지, 병렬 채팅의 본보기가 아니다.

## 6. 손익



### 장점

- 한 채팅의 조사·서류가 끝나기 전에 다른 채팅에서 IDE나 다른 조사를 시킬 수 있다.
- 채팅을 옮겨도 진행 중 답이 취소되지 않는다.
- 기록 저장은 이미 대화별이라, 실행만 세션에 붙이면 된다.
- 파일 사본을 쓰면 Cursor와 같이 본 작업 트리를 더럽히지 않고 코딩 작업을 겹칠 수 있다.



### 단점과 리스크

- Hermes 전역 모델을 그대로 두면, 모델이 다른 두 채팅이 서로의 요청을 덮어쓴다.

  **헤르메스 구조를 바꾸면 풀리나.** 헤르메스 소스를 고칠 일은 아니다. 헤르메스는 이미 요청마다 모델을 받는다. 아이리스가 매 턴 `set_inference_model`로 런타임 기본 모델을 통째로 바꿔서, 다음 채팅의 설정이 이전 채팅의 요청을 덮는다. 아이리스가 그 전역 쓰기를 멈추고, 그 요청에만 `model`과 `provider`를 실으면 이 항목은 끝난다. 확인 내용은 8절이다.

- 잠금 없이 IDE·파일 쓰기를 열면 두 세션이 같은 파일을 동시에 고친다. Claude 공개 문서도 스레드 기록은 나누면서 샌드박스 파일은 공유할 수 있다고 적는다. Iris는 그 공유가 기본이다.

  **샌드박스 파일.** Claude Managed Agents 문서의 샌드박스는, 에이전트가 그 세션 동안 읽고 쓰는 임시 디스크다. 대화 기록은 스레드마다 달라도, 그 디스크는 여러 스레드가 같이 쓸 수 있다고 적혀 있다. 아이리스에는 그 임시 디스크가 없다. 채팅들이 처음부터 같은 프로젝트 폴더, 같은 위키 보관함을 본다. 그 공유가 기본이라는 뜻이다. 장점은 사용자가 여는 파일이 곧 작업 결과이고, 노트는 합치는 단계가 없다는 것이다. 단점은 두 채팅이 같은 파일을 같이 고치면 서로 덮어쓴다는 것이다. 그래서 쓰기는 잠금 또는 worktree로 나눈다.

- 로컬 GPU·Ollama는 루프를 늘려도 처리가 직렬에 가깝다. 병렬은 대기 취소가 없어지는 이득이지, 두 배 속도가 아니다. 평소 경로가 원격 API이면 이 항은 그 특수 상황에만 해당한다. 원격의 한 모델은 5절 6항처럼 요청을 여러 건 받는다.

  **vLLM 같은 병렬 엔진.** vLLM은 한 GPU에서 같은 모델의 요청을 배치로 겹쳐 처리량을 올린다. Ollama 기본 큐보다 로컬 동시 요청에 맞다. 세션 분리, 파일 잠금, 전역 모델 덮어쓰기를 대신하지는 않는다. 1단계를 넣은 뒤 로컬에서 두세 채팅의 대기가 길 때 검토할 엔진이다. 채팅 수가 사람의 주의력 안에 있으면, 엔진 교체보다 세션 분리가 먼저다. 원격 API를 쓰면 그 서버가 이미 요청을 병렬로 받는다.

- 클라우드 세션·주간 한도는 채팅 수만큼 빨리 소모된다.
- 백그라운드 세션의 도구 승인 창이 포그라운드 작업을 가릴 수 있다. 승인은 그 세션에 속해야 한다.
- 음성·전역 마이크는 여전히 하나다. 말을 어느 채팅에 넣을지 규칙을 정하지 않으면 백그라운드 세션으로 새지 않는다.

  **음성 규칙.** 마이크도 TTS도 창에 하나다. 기준은 지금 화면에 있는 채팅이다. 음성 인식 결과는 그 채팅으로만 들어간다. TTS도 그 채팅의 답을 읽는다. 다른 채팅으로 옮기면 읽던 TTS는 멈춘다. 옮겨 간 채팅에서, 자리를 비운 동안 작업이 끝나 새 답이 있으면 그 답을 한 번 읽는다. 뒤에 있던 채팅이 끝났다고 해서, 보고 있지 않은 화면의 TTS가 끼어들지는 않는다. 두 채팅이 동시에 끝나 있으면, 지금 연 채팅만 읽는다.

- worktree를 성급히 넣으면 의존성 설치와 결과 병합이 새 장애가 된다. Cursor 문서도 결과를 본 트리로 되돌리는 단계를 따로 둔다.

## 7. 권고

1단계는 세션별 루프와 전환 시 취소 제거, 동시 2개, 파일·IDE 쓰기는 잠금 하나다. 이 단계만으로 조사와 서류는 채팅마다 동시에 가고, 코딩은 한 채팅만 쓴다.

2단계는 요청 단위 모델이다. 채팅마다 다른 모델을 쓸 때 필요하다.

3단계는 코딩 병렬이다. Git worktree로 세션별 사본을 만들고, 끝나면 사용자가 본 트리로 가져온다. 그 전에 자동 병합은 넣지 않는다.

**Git worktree.** Git에 들어 있는 명령이다. 따로 설치하는 라이브러리가 아니다. `git worktree add <다른 폴더> <브랜치>`를 치면, 커밋 이력은 저장소 하나이고 작업 폴더는 두 개가 된다. A 폴더에서 `main.py`를 고쳐도 B 폴더의 `main.py`는 그 순간 그대로다. 각 폴더는 자기 미저장 변경을 가진다. 아이리스가 할 일은 코딩 세션이 시작될 때 이 명령을 호출하고, 그 세션의 IDE와 터미널만 그 폴더를 보게 하는 것이다. 끝나면 사용자가 그 차이를 원래 폴더로 가져온다. Cursor 문서를 베끼는 부분은 「에이전트마다 폴더를 나누고, 합치기는 사람이 한다」는 순서다. Cursor의 화면 코드를 가져오지는 않는다.

**위키로 이 사본을 만들 수 있나.** 없다. 위키는 노트다. `projects/<슬러그>/chats/<대화 id>.md`는 그 채팅의 글이지, 컴파일되는 소스 체크아웃이 아니다. 채팅마다 노트가 이미 나뉘므로, 위키 조사와 서로 다른 노트 쓰기는 3단계 없이 1단계 세션과 경로 잠금으로 된다. 3단계가 필요한 것은 같은 코드 저장소를 두 채팅이 동시에 고칠 때뿐이다.

## 8. 바꾸는 층과 프레임워크

프레임워크를 바꾸지 않는다. Hermes를 LangGraph·AutoGen·Claude Agent SDK 같은 다른 에이전트 런타임으로 갈아끼우는 일이 아니다. Hermes 프로세스, `iris/system/hermes_gateway.py`의 기동·헬스, `iris/core`(파서·인용·활동 기록)도 이 변경의 본체가 아니다.

막는 것은 아이리스가 창 하나에 실행 슬롯을 하나만 둔 부분이다.


| 층                | 이 변경에서                                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 아이리스 채팅 실행       | 본체. `ChatTurnGate`, `UserTurnDispatcher`, `MainWindow._chat_worker`, `_load_conversation`의 `conversation_switch` 취소. 대화 id마다 워커·점유·부분 응답을 둔다.            |
| 아이리스 → Hermes 호출 | 2단계만. `HermesChatWorker`가 매 턴 `set_inference_model`(`scope: main`)로 런타임 기본 모델을 통째로 바꾼다. 채팅마다 모델이 다를 때 이 전역 쓰기를 요청 단위로 바꾼다. 1단계(같은 모델, 동시 2개)는 그대로 둬도 된다. 이 칸의 의미는 아래 「요청 단위 모델」에 있다. |
| Hermes 게이트웨이     | 프로세스 하나를 그대로 쓴다. 기동·재시작·포트 진단을 여러 게이트웨이로 쪼개지 않는다.                                                                                                        |
| Hermes 자체        | 소스·루프·도구 구현을 고치지 않는다. 아래 공개 API가 이미 동시 실행과 세션을 받는다.                                                                                                      |
| `iris/core`      | 손대지 않는다. 스케줄이 여기 없다.                                                                                                                                     |


아이리스가 지금 보내는 `POST /v1/chat/completions`의 `model`만으로는 요청 단위 모델이 되지 않는다. 공개 API 서버 문서는 `provider` 없는 `model`을 기본으로 무시하고, 게이트웨이 기본 모델로 떨어뜨린다. `provider`를 같이 보내거나, 세션 채팅·`/v1/runs`를 써야 그 요청의 모델이 적용된다. `direct_model_requests: true`는 그 무시를 끄는 설정이지, 아이리스가 전역 `set_inference_model`을 계속 호출해도 되는 이유는 아니다.

**요청 단위 모델은 어디에 있나.** 헤르메스 런타임이 「호출하면 항상 기본 모델만 통째로 바뀌는」 구조는 아니다. 기본 모델을 바꾸는 API와, 그 요청에만 모델을 싣는 API가 둘 다 있다. 아이리스가 전자만 쓰고 있다. `HermesClient.set_inference_model`이 `POST /api/model/set`에 `scope: main`을 보내 게이트웨이 기본 모델을 덮어쓴다. 채팅 두 개가 이 쓰기를 번갈아 하면 서로의 기본 모델이 바뀐다.

바꿀 일은 아이리스의 호출이다. 매 턴의 전역 `set_inference_model`을 멈추고, 그 요청에 `model`과 `provider`를 함께 보낸다. 받는 곳은 이미 있는 `POST /v1/chat/completions`, `POST /v1/runs`, 세션 채팅이다. 헤르메스에 새 기능을 구현하거나, 헤르메스 루프 소스를 수정하는 일이 아니다.

2026-10-08에 공개 문서 `website/docs/user-guide/features/api-server.md`(커밋 `a28a5d03`)의 「Per-request model selection」을 다시 봤다. `model`, `provider`, `model_options`를 채팅 완료·responses·runs·세션 채팅에 실을 수 있고, 우선순위는 세션 덮어쓰기 → 라우트 별칭 → 요청 필드 → 전역 기본이다. `provider`가 있으면 `direct_model_requests` 없이도 그 요청의 모델이 적용된다. 이 항목은 최근 문서에 있다. 세션마다 모델을 자동으로 나눠 주는 `session_model_pool`(NousResearch/hermes-agent#37519)은 여전히 1·2단계의 전제가 아니다.

설치본 게이트웨이가 아래 헤더·상한을 실제로 광고하는지는 작업 전에 `/v1/capabilities`와 `gateway.api_server.max_concurrent_runs`로 확인한다. 문서 기준으로 기본 동시 실행 상한은 10이고, 넘으면 HTTP 429다. 아이리스 권고(동시 2 또는 3)는 그 안에 있다.
