# 다중 채팅 동시 작업 2단계 분석 보고서

| 항목 | 내용 |
|---|---|
| 문서 번호 | IRIS-REV-2026-1012-01 |
| 작성일 | 2026-10-12 |
| 관련 | IRIS-IMPL-2026-1011-01, `docs/prompts/다중채팅-동시작업-2단계-구현프롬프트.md`, IRIS-REV-2026-1011-01 |
| 대상 | Iris Light 메인 채팅 2단계 |
| 목적 | 2단계 완료 기준을 소스와 대조해 된 것, 안 된 것, 보안·개선을 가른다 |

대조 기준은 구현 프롬프트다. 구현 보고서 4절은 착수 전에 쓰였고, 설치본 확인 뒤 세션 헤더와 동시 2가 프롬프트에서 바뀌었다. 2026-10-12에 `tests.test_request_model`, `tests.test_hermes_model_failover` 16건, `python -m iris.ui._check_conversation_switch_cancel`, `python -m iris.ui._check_turn_followup`을 실행했다. 모두 통과했다.

## 1. 결론

2단계는 채팅마다 모델 이름을 기억하고, 메인 채팅 스트림이 게이트웨이 기본 모델을 덮어쓰지 않게 하는 일이다. 그 본 경로는 들어가 있다. 슬롯이 런타임 id를 기억하고, `HermesChatWorker.run`은 `set_inference_model`을 부르지 않으며, `provider`가 있으면 광고 이름이 하나여도 요청 모델명을 유지한다.

모델 이름만 갈라진다. 주소와 키는 여전히 게이트웨이 설정 한 칸이다. 화면 피커·접속 확인·제목·루틴·인수인계가 그 칸을 `set_inference_model`로 다시 쓴다. 이미 보낸 HTTP 본문은 바뀌지 않아도, 처리 시점의 설정 주소와 키는 바뀐다.

세션 헤더를 빼 둔 것은 누락이 아니다. 헤더가 있으면 게이트웨이가 본문의 이전 턴을 `state.db` 기록으로 바꾼다. 프롬프트가 그 헤더를 넣지 말라고 했고, 코드와 검사가 그 쪽이다.

## 2. 구조

```text
전송 _execute_user_turn_body
  └─ choose_turn_model
       ├─ 이어하기 + 저장값 → 피커를 부르지 않음
       └─ 사용자 턴 또는 빈 슬롯 → 피커 값을 슬롯에 기록
            └─ 클라우드 미로그인일 때만 저장값을 로컬 모델로 다시 씀
                 └─ _launch_chat_turn_bound
                      └─ resolve_hermes_inference(런타임 id)
                           ├─ 페이로드 model = 업스트림 이름
                           ├─ 페이로드 provider = custom
                           └─ base_url·api_key 는 본문에 없음     ← 기준이 갈라지는 곳
                                └─ HermesChatWorker.run
                                     └─ set_inference_model 없음
                                          └─ POST /v1/chat/completions
화면 피커·게이트웨이 접속
  └─ HermesModelSyncWorker → set_inference_model     ← 설정 한 칸을 덮음
제목·루틴·인수인계
  └─ backend_call._hermes
       ├─ set_inference_model
       └─ stream_chat (provider 없음) → 광고 이름 하나
```

갈라지는 지점은 완료 요청이 `model`과 `provider`만 싣고, 주소와 키는 마지막 `set_inference_model`이 쓴 설정에 남는 곳이다.

## 3. 코드 리뷰

| 기준 | 판정 | 근거 |
|---|---|---|
| 1. 슬롯이 런타임 id를 기억한다. 이어하기는 저장값만 쓰고 피커를 부르지 않는다 | 본 경로 충족 | `choose_turn_model`. 사용자 턴은 피커 값으로 저장값을 덮는다. 빈 이어하기만 피커를 한 번 쓴다. 클라우드 미로그인이면 그 다음에 `slot.inference_model`을 로컬 이름으로 다시 쓴다 |
| 2. 메인 채팅 `HermesChatWorker.run`이 `set_inference_model`을 호출하지 않는다 | 충족 | `run`은 `stream_chat(target.model, provider=)`만 호출한다. 검사 16건이 호출 횟수 0을 본다 |
| 3. `provider`가 있으면 광고 모델이 하나여도 슬롯에서 푼 모델명을 유지한다 | 채팅 스트림만 충족 | `stream_chat`은 `provider`가 있으면 `resolve_request_model`을 타지 않는다. `provider`가 없으면 광고 이름 하나로 바뀐다. 제목·루틴·인수인계는 `provider` 없이 호출한다 |
| 4. 완료 페이로드의 `model`은 업스트림 이름이다. 런타임 id를 넣지 않는다 | 충족 | `stream_model = target.model`. 런타임 id는 슬롯과 폴백 후보의 라벨에만 있다 |
| 5. 페이로드와 로그에 `api_key`와 `X-Hermes-Session-Id`가 없다 | 충족 | 본문 키는 `model`, `messages`, `stream`, 그리고 `provider`가 있을 때만 `provider`. `trace_payload`는 키 이름·바이트·해시·글자 수만 남긴다. 검사도 헤더 없음을 본다 |
| 6. 화면을 옮긴 뒤의 첨부·자료·이전 대화 검색은 그 턴의 대화에만 글을 쓴다. 프롬프트 칸은 슬롯에 있다 | 충족 | `_continue_user_turn`, `_on_material_read_done`, 이전 대화 `proceed`, `_launch_chat_turn`이 `_enter_owning`으로 다시 묶는다. 프롬프트 칸 9개는 `SlotAttr`이다. 이 경로는 2단계가 새로 만든 것이 아니고, 2단계가 창 필드로 되돌리지도 않았다 |
| 7. `CAP` 8, 동시 10, 전환은 워커를 취소하지 않는다 | 충족 | `CAP = 8`, `MAX_CONCURRENT = 10`. 전환 검사와 이어하기 검사가 통과했다. 구현 보고서의 동시 2는 프롬프트가 10을 유지하라고 바꿔 두었다 |

충족 경로에서 하지 않은 일. 헤르메스 소스 수정, `direct_model_requests`, Sessions API, `X-Hermes-Session-Key`, 메일 패널의 `ChatRunMap` 흡수, Git worktree. `inference_provider`는 발사 때 한 번 저장하고, 다음 요청은 그 필드를 읽지 않고 `resolve_hermes_inference`를 다시 탄다.

구현 보고서 4절 3번(세션 헤더에 대화 id)은 철회된 기준이다. 코드가 헤더를 빼 둔 것이 그 기준의 미완료가 아니다.

### 주소와 키가 갈라지지 않는 호출

`resolve_hermes_inference`는 Ollama와 등록 API를 모두 `provider="custom"`으로 푼다. 둘을 가르는 값은 `base_url`과 `api_key`다. `stream_chat`은 그 둘을 본문에 넣지 않는다.

| 호출 | 채팅이 도는 동안 하는 일 |
|---|---|
| `HermesModelSyncWorker` | 피커를 바꾸거나 게이트웨이가 접속되면 `set_inference_model`. 설정에 그 타깃의 주소와 키를 쓴다 |
| `backend_call._hermes` | 제목·루틴·인수인계가 같은 쓰기를 한 뒤, `provider` 없는 `stream_chat`을 보낸다. 광고 모델이 하나면 이름이 `hermes-agent`로 바뀐다 |
| `hermes_ollama_guard` | 모델 전환 뒤 `ollama_num_ctx`를 맞출 때 `set_inference_model`을 다시 호출할 수 있다 |

채팅 A의 POST 본문은 A의 모델명으로 이미 나간다. 그 사이 B의 피커 동기화나 제목 작업이 설정을 덮으면, 게이트웨이가 요청을 처리할 때의 custom 주소와 키는 B 쪽일 수 있다.

## 4. 보안

| 항목 | 내용 |
|---|---|
| 주소·키 공유 | 채팅 둘의 완료 요청은 둘 다 `provider=custom`이다. 업스트림 주소와 키는 설정 파일 한 칸이다. 마지막 `set_inference_model`이 그 칸의 주인이다 |
| 설정 다시 쓰기 | 피커 변경, 게이트웨이 재접속, 제목·루틴·인수인계가 진행 중 채팅의 설정 키를 덮어쓴다. 채팅 워커 자신은 이 쓰기를 하지 않는다 |
| 부수 호출의 모델 무력화 | `backend_call._hermes`는 `provider`가 없다. 광고 모델이 하나면 의도한 업스트림 이름이 광고 이름으로 바뀐다 |
| 세션 공유 | `X-Hermes-Session-Id`를 보내지 않는다. 아이리스가 보낸 이전 턴은 유지된다. 게이트웨이 기본 세션의 도구·기억은 채팅 둘이 같이 쓴다 |
| 키 노출 | 완료 본문·`trace_payload`·활동 줄에 키 값은 없다. 키는 `set_inference_model`이 설정 파일 `model.api_key`에 남긴다. CLI argv에는 넣지 않는다 |
| 저장 필드 | `inference_provider`는 요청이 읽지 않는다. 다음 턴은 DB의 API 행을 다시 푼다. 그 사이에 행이 바뀌면 이어하기의 주소도 바뀐다 |
| 잠금 대기 | `acquire_project` / `acquire_wiki`는 타임아웃이 없다. 2단계 범위 밖이다. 쥔 요청이 반환되지 않으면 그 대화 밖에서 쓰기가 멈춘다 |
| 표 밖 쓰기 | `ide.open_file`, `ide.marketplace_install`, `ide.set_project_root`는 잠금 표에 없다. 2단계 범위 밖이다 |

키 값을 이 문서에 적지 않는다.

## 5. 개선안

2단계 안에 남은 빈 자리.

1. 완료 요청이 모델 이름과 `provider`만 가지고, 업스트림 주소와 키는 게이트웨이 설정 한 칸인 자리.
2. 제목·루틴·인수인계의 `backend_call._hermes`가 그 칸을 `set_inference_model`로 덮고, `provider` 없이 스트림을 보내는 자리.

2단계 밖으로 남은 빈 자리. 잠금 대기 시간, 표 밖 IDE 액션. 세션 헤더를 지금 POST에 넣는 자리는 비워 둔다. 넣으면 이전 턴이 게이트웨이 기록으로 바뀐다. 헤르메스 소스를 고치지 않는 한 그 헤더는 개선이 아니다.

Git worktree는 이 구멍과 무관하다. 주소가 하나인 문제는 폴더 사본으로 갈라지지 않는다.

## 6. 차용

| 이름 | 가져올 부분 | 이 분석에서 가져오지 않는 이유 |
|---|---|---|
| 헤르메스 요청 단위 `model`·`provider` | 이미 채팅 워커에 들어 있다 | 다시 넣지 않음 |
| `set_inference_model` 유지 경로 | 피커·설정의 기본 모델 동기화만 | 채팅 런마다 다시 켜지 않음. `direct_model_requests`로 우회하지 않음 |
| `X-Hermes-Session-Id` | 없음 | 본문 이전 턴을 `state.db`로 바꾸므로 넣지 않음 |
| 요청 본문의 `base_url`·`api_key` | 확인하지 못함 | 설치본이 그 필드로 설정 파일을 안 쓰는지 이번 대조에서 다시 열지 않음. 키를 로그에 싣는 안은 쓰지 않음 |
| Git worktree | 없음 | 모델 이름 분리와 무관 |
| 다른 에이전트 SDK | 없음 | 호출 형식의 남은 칸은 주소·키 한 칸과 부수 호출이다 |

---

## 7. 조치

1. 세션 헤더 없음을 2단계 미완료로 되돌리지 않는다.
2. 다음 수정이 있으면 `backend_call._hermes`의 `set_inference_model`과 `provider` 없는 스트림부터 본다. 채팅 워커에 이미 있는 경로를 다시 만들지 않는다.
3. 서로 다른 API 주소 둘을 동시에 격리됐다고 보지 않는다. 설정 한 칸이 남아 있다.
4. 잠금 표와 worktree는 이 수정과 한 묶음으로 넣지 않는다.
